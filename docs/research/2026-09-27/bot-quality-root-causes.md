# Research 27 Sep 2026: bot-quality-root-causes

> Raw findings from the 27 Sep research run (read-only agents). The fact-check pass did not run (session limit); four key claims were checked by hand afterwards: GPT-6 Luna price and function-calling rule (its release date is 18 May 2026, not 22 Sep), Kimi line-up and retirements, Meta charging service messages from 1 Oct 2026, Shopify's `shopifyapp` package. Everything else: re-check against the linked source before relying on it. Decisions drawn from this are in /plan.md.

## Says it did something it did not do (add, remove, pay), or did something different
Actions are described in the model's free text and checked afterwards by an English regex that only knows cart verbs. Nothing compares what the text claims with what the tools actually did. (a) Payment: the assistant has no checkout tool, and AssistantReply has no cta_url or action field. A Pay Now button can only come from the CHECKOUT/BUY code paths, so 'Here's your secure Pay Now button' is a claim nothing can back. _CLAIMS_CART_CHANGE contains no pay, order, button or link words. The success text of tool_add_to_cart itself tells the model 'They can reply CHECKOUT to pay'. (b) Quantity: remove_from_cart takes only product_id. It deletes every cart line of that product, in every size, even though repo.update_cart_item already supports a quantity. The claim guard lets 'Removed 2' through because a remove did succeed, and the number in the text is never compared with the tool result. (c) 'Reply CHECKOUT' on an empty cart comes from prompt line 78, which tells the model to deflect whatever the cart holds.

## Size handling: invented size options, fit advice from nothing, asking again for a size just given
The model sees a product's real sizes only when it calls a tool. The CUSTOMER block lists the last list shown and the picked item as 'id name' with no sizes, and the '[Showed: ...]' memory line has none either. So when the model asks 'which size?' without calling get_product_details, it falls back to a generic S-XXL. Money is checked (_unverified_amounts) but sizes are not: nothing verifies that a size named in a reply belongs to that product. Fit advice ('5'8 -> M or L') cannot be verified at all. data/products.json has only sizes_available and stock (no size chart, no measurements), and no tool exposes one, so prompt rule line 82 is the only barrier. The code-side size path needs a cue word, and _SIZE_CUE has no typo tolerance, so 'i want 11 sizr' went to the model. The model (gpt-oss-20b, reasoning low) asked again instead of calling add_to_cart, although _size_was_said would have accepted '11' for 'UK 11'.

## Constraints lost or borrowed across turns (wrong category, stale budget, invented person, profile ignored)
There is no structured 'current request' state. The model gets the last 8 raw messages, each cut to 350 characters, with no topic boundaries, and has to work out who, what and budget again on every turn. Filters come only from the arguments the model writes: tool_search_products parses the MODEL's query string and prefers the model's max_price. So the Rs 5,000 from the sister's haldi request was silently reused. Nothing checks that a budget in the tool arguments appears in the customer's words for the current request, as _size_was_said does for sizes. A category named two turns back is lost once the model writes a query without it ('accessiroes' is also a typo parse_query cannot map). Retrieval then hard-excludes Footwear, Bags and Headwear whenever no category is set, so accessories cannot come back at all. Profile notes are free text in the prompt, and the search tool never reads them. The gender in 'man' was not saved because _facts_to_keep rejects it when any other person appears in the last three customer messages. The invented friend is the model copying its own earlier reply from the raw history.

## Products that do not fit the stated need (colour, occasion, night vs daytime, groom vs guest)
Colour is not a filter anywhere. Filters has no colour field, the search_products schema has no colour parameter, and catalogue colours are free text ('Midnight teal', 'Black multicolour') with no colour family. Colour therefore lives only in one MiniLM vector over a long document, where 'black' is outweighed by category and occasion words. Occasion is taken only from the model's query text. normalise_filters accepts an occasion, but the tool neither exposes nor passes one, so when the model's query dropped 'haldi', the occasion-first sort never ran. That sort is binary and keys on the first recognised occasion word. 'night' and 'guest' are not recognised, even though the data has 'Evening', 'Formal evening', 'Wedding guest' and 'Groom' tags. Phrases like 'for a daytime or summer wedding' exist only in description text, which a bi-encoder cannot contrast with 'night'. The model is shown 6 candidates and picks 2-4, and nothing checks that its picks meet the stated constraints.

## Payment deflection: 'Reply CHECKOUT' instead of checking out
This is the designed behaviour. The prompt says 'tell them to reply CHECKOUT', no tool can check out, and the add_to_cart result repeats 'They can reply CHECKOUT to pay'. The code-side catcher is an exact phrase set plus a whole-message regex. _CHECKOUT requires 'want/like/wanna TO', so 'i wanna checkout' fails. There is no edit-distance tolerance ('chedckout', 'checkot'), and 'proceed to payment' is not in the list ('proceed to pay' is). Anything it misses goes to the model, which can only deflect.
refs: backend/bot/assistant.py:78, backend/bot/assistant.py:137-172, backend/bot/assistant.py:287-288, backend/selection.py:230-233, backend/selection.py:249-252, backend/selection.py:268-275, backend/routers/webhook.py:243-259

## Guard-cut sentence fragments
_without_listing cuts the model's sentence after the fact, at the first product name next to a rupee amount, instead of asking the model to rewrite. adb0f6b added a changed_cart exemption and a 'too short to be a sentence' rule, but it is still string surgery on English text. _drop_sentences_with handles bad amounts the same way. The model writes names and prices in the first place because the prompt forbids them in a single line of prose, and the list that code attaches is out of the model's sight.
refs: backend/bot/assistant.py:398-425, backend/bot/assistant.py:607-612, backend/bot/assistant.py:637-645, backend/bot/assistant.py:71

## Cart and order answers that are confusing or duplicated
The webhook appends the code-rendered cart or orders block after the model's own words with no de-duplication. The model also has the full cart in its context, so it summarises the cart too. send_reply accepts any valid product ids, so cart items sent as product_ids render as a shopping list with 'Reply 1-N to choose'. cart['count'] counts units (sum of quantities) while the cards show lines, which produces '4 items' above 2 cards. _is_lookup only catches short phrasings such as 'my cart' or 'what's in my', so 'what 4 items do i have' reached the model.

## Misreading who will wear it; asking the wrong question and skipping the budget
Who wears the outfit is guessed by stacked English, wedding-specific regexes (_OTHER_PERSON, _THEIR_FUNCTION, _WEARS_IT_THEMSELVES, _wearer). The result becomes a prompt hint that the model follows only in part: it asks 'who' and drops 'and their budget'. For 'haldi outfits for my brother', parse_query already sets gender=Men, so _who_hint returns nothing, and the budget question was the model's own choice, against its own prompt example (line 70). The raw history lets the model repeat its earlier question word for word. Weak instruction-following in the live setting (gpt-oss-20b with reasoning_effort=low) makes both worse.
refs: backend/bot/assistant.py:684-716, backend/bot/assistant.py:759-780, backend/bot/assistant.py:69-70, backend/bot/assistant.py:790, backend/.env:31-32

## Off-topic boundary wrong in both directions
Both directions were patched rather than designed. A shape regex replaces any reply that looks like code; that part is generic and carries over to any shop. Address questions are answered in code before the model sees them. The prompt's off-topic rule and the OFF_TOPIC text are hard-coded to 'ethnic wear', so they must become brand configuration.
refs: backend/bot/assistant.py:79-80, backend/bot/assistant.py:430-438, backend/bot/assistant.py:825-827, backend/routers/webhook.py:918-925, backend/routers/webhook.py:1018-1030

## Typos defeat the code-side parsers
Every code-side parser matches exact tokens or whole-message regexes: the _GARMENTS and _OCCASIONS dictionary lookups, the command phrase sets, _SIZE_CUE, _ASKS_REORDER, and the address regex (which lists 'adress' and 'addres' by hand). There is no normalisation step, such as spelling correction against the catalogue's vocabulary or trigram similarity. So 'shervani', 'accessiroes', 'weeding', 'chedckout' and 'sizr' change the route or lose a filter. The LLM copes with typos, but it only sees what this layer passes on, and the plain-search fallback (bot/chat.py) relies on parse_query alone.

## Owner training can teach the bot defective replies
guidance() turns the first paragraph of any thumbs-up reply into a 'You:' few-shot example for questions at cosine >= 0.65 (SIMILAR - 0.1). The stored answer is the full rendered text the webhook logged, including guard-cut fragments and borrowed budgets, and the owner's thumbs-up meant 'good products', not 'copy this wording'. Lookups use different keys from ratings. The admin page rates a short follow-up as 'earlier + question', but at answer time guidance is looked up with the bare customer message, and ranking_adjustments with the model's search query string. SIMILAR = 0.75 was set for MiniLM, and on short texts budget-only messages ('around 7k' vs 'around 10k') score above it, so product boosts leak between unrelated requests.
refs: backend/training.py:36, backend/training.py:113-127, backend/training.py:130-146, backend/routers/admin.py:62-67, backend/bot/assistant.py:648-666, backend/bot/assistant.py:806, backend/bot/retrieval.py:465, backend/routers/webhook.py:842, backend/routers/webhook.py:851

## (Latent) Photos and voice notes get no reply at all
receive_message drops every message that is neither text nor a button reply, logging only a server print ('unhandled image message'). The customer gets no answer, not even 'I cannot open photos yet'. whatsapp.py can upload media (media_id_for) but has no media download. The text path assumes message['text']['body'], so every later stage (memory, logging, _handle_text) is text-only.
refs: backend/routers/webhook.py:1141-1147, backend/routers/webhook.py:1153, backend/routers/webhook.py:1099-1114, backend/whatsapp.py:142-174

# LEVERS
- [high, 3d] 1. Conversation-level eval harness built from the logs: live model, scripted multi-turn conversations, state-diff assertions plus a calibrated LLM judge (details in eval_proposal). Build it first: every other lever, and the Kimi decision, needs it.
  fixes: Makes all 11 failure modes measurable before and after a change. It is the only sound way to choose between gpt-oss-120b and Kimi, and to delete regex heuristics safely. It generalises fully: the case files are per brand.
  risk: LLM judges are lenient (the owner's thumbs-ups approved fragments), so most checks must be deterministic and the judge calibrated against owner labels. Fixtures break when a catalogue changes, so write the T-shirt set against the pilot's real Shopify export. Runs need Groq's paid tier, about $1-5 per full matrix.
- [high, 1d] 2. Checkout as an action, not advice: a checkout tool that code implements, the deflection removed from the prompt, and a wider, typo-tolerant CHECKOUT matcher
  fixes: Payment deflection; the false 'Here's your Pay Now button'; promising a checkout on an empty cart. How: delete prompt line 78 and the 'They can reply CHECKOUT' text in the add_to_cart result (assistant.py:288). Add a checkout tool with no arguments whose code calls the existing _handle_cart_command('checkout'), which already handles missing sizes, the address flow and an empty cart, and returns a Reply with cta_url that the webhook sends unchanged; AssistantReply gets an action/cta field. Widen _CHECKOUT to accept 'wanna/want' without 'to' and 'proceed to payment', and allow an edit distance of at most 2 on one- or two-word messages ('chedckout', 'checkot'). Generalises: yes. For Shopify the same tool returns the Storefront API cart checkoutUrl instead of a Razorpay order.
  risk: Low: paying still needs the customer's own tap. Gate the tool on the current message expressing an intent to pay, so a stray call cannot create unpaid orders (repeat CHECKOUTs already reuse the unpaid order).
- [medium, 0.1d] 3. Reply to photos, voice notes and other media instead of staying silent
  fixes: The latent silent drop at webhook.py:1145. Until levers 10 and 16 land, answer non-text types with one line: 'I can't open photos or voice notes yet, please type what you're looking for.'
  risk: None.
- [high, 1.5d] 4. Action ledger: confirmations written by code, cart tools that take quantity and size, and claim checks extended to payment and orders
  fixes: 'Says it did something it did not do' and 'did something different' ('Removed 2' when 3 went); the duplicated cart. How: remove_from_cart(product_id, size?, quantity?) plus set_quantity, both using repo.update_cart_item. Each state-changing tool records a structured effect {op, product, size, qty_before, qty_after}, and the webhook writes the confirmation line from that record ('Removed 2 x Aqua Chanderi Saree, 1 left. Cart: Rs X'). The model's message keeps only wording that carries no facts. Extend the claim check to pay, order, button and link words, and to quantities (a number beside a product name must equal the recorded quantity). When attach is set, drop model lines that restate the attached data. Generalises: yes, it does not depend on the catalogue. Claim words need per-language lists, or the model must report its own claims in a structured field.
  risk: Low to medium. 'Remove it' needs a default (the whole line unless a number is given), with tests. Regex claim detection stays English-only, so rely mainly on code-written confirmations.
- [high, 1.5d] 5. Sizes as checked facts, plus a size-guide tool
  fixes: Invented size options, fit advice with no basis, asking again for a size just given. How: put in-stock sizes into the CUSTOMER block for the last list shown and the picked item, and into memory_text. Add a size check like _unverified_amounts: a size named in the reply for the product in focus must be one of its sizes, otherwise retry once and then strip it. Add get_size_guide(product_id), backed by a per-brand size chart (a CSV the brand uploads in its dashboard: size to chest, length and waist per product type, or a Shopify metafield if one exists), with the prompt rule 'fit advice only from get_size_guide, otherwise ask their chest size or usual size'. Map size typos and number words. Generalises: yes, and it matters more for T-shirts and activewear, where fit is the main question and returns cost a small brand most.
  risk: Many Shopify stores keep size charts only as images, so brands will enter them by hand. The model may still give advice anyway, so the size check and a judge criterion stay necessary.
- [medium, 0.5d] 6. Model A/B via configuration: gpt-oss-120b at reasoning medium as the primary, against Kimi K2.6. This answers the Kimi question.
  fixes: Failures that are about model behaviour: dropping the budget half of a hint, repeating history, not calling add_to_cart for '11 sizr', following several constraints at once. Step 1 needs only .env changes: LLM_MODEL=openai/gpt-oss-120b and LLM_REASONING_EFFORT=medium, with fallbacks gpt-oss-20b, then qwen3.8-27b. Step 2: add Kimi through Moonshot's OpenAI-compatible API or OpenRouter. The code would need a base_url and key per model (today there is one LLM_BASE_URL), and the Groq-specific repair in _salvage must be re-checked. Facts about Kimi (third-party listings; verify before deciding): Groq deprecated Kimi K2 in March 2026 and pointed users to gpt-oss-120b (console.groq.com/docs/deprecations). K2.5 was retired on 31 Aug 2026. K2.6 is listed at about $0.95 in / $4 out per million tokens, and K3 at about $3 / $15 with thinking always on (openrouter.ai/moonshotai/kimi-k2.6, benchlm.ai/moonshot/api-pricing). Estimated cost per customer message (about 6.5k tokens in, 0.4k out): gpt-oss-20b about $0.0006, gpt-oss-120b about $0.0012, K2.6 about $0.008, K3 about $0.026. At 3,000 messages a month that is roughly Rs 160, Rs 320, Rs 2,000 and Rs 6,700. Only gpt-oss-120b fits a Rs 1,000 total alongside hosting. Kimi is not needed for images or voice: Groq's qwen/qwen3.8-27b, already the third fallback, accepts images with tool use and JSON mode (console.groq.com/docs/model/qwen/qwen3.8-27b), and Groq's whisper-large-v3-turbo does speech-to-text for about $0.04 per hour (console.groq.com/docs/model/whisper-large-v3-turbo). Moonshot offers no speech-to-text API.
  risk: Cost and latency (K3's thinking cannot be switched off). Kimi adds a second provider and sends customer data to a China-based provider, which needs DPDP notice and consent for chats, photos and voice. A prompt tuned for gpt-oss may behave differently. A model switch fixes none of the orchestration causes. Groq's free tier (8k tokens per minute per model) cannot serve a pilot whatever the model, so move to the paid Developer tier.
- [high, 2d] 7. Colour and attribute filters that are enforced, filled from the customer's own words and passed through the tool
  fixes: Products that do not fit the need: a request for black returning ivory, occasion lost when the model's query drops it, night vs daytime, groom vs guest. For T-shirts: colour, fit (oversized, regular, slim), activity (gym, running, yoga), fabric (dri-fit, cotton), sleeve, neck. How: at ingest, derive colour_family from the colour string or Shopify's Color variant option (a small map, with a one-time LLM fallback per product). Extract per-brand attribute facets from descriptions once, with an LLM, into a JSON column. Add colors, occasion and attributes parameters to search_products, checked against the catalogue's values (unknown values dropped or fuzzy-mapped). Merge a parse of the customer's current request with the model's arguments, instead of relying on the model's query text alone. When a colour is not stocked, relax the filter and say so, as the budget relax already does. Check that every product shown meets the stated filters. Generalises: yes, because the vocabulary comes from each catalogue.
  risk: Over-filtering on small catalogues, so the relax order needs tests. Attribute extraction will make mistakes, so let the owner edit facets in the dashboard.
- [high, 3d] 8. Structured 'current request' state that resets on a new topic, replacing the 8 raw history messages as the source of constraints
  fixes: Stale budget, borrowed person ('your friend'), a category lost across a clarifying question (accessories), profile ignored, repeating old replies. How: sessions.brief as JSON {for_whom, gender, category, colour, occasion, budget_min/max, size}, updated through a field on send_reply/search_products. Code checks it against the catalogue's values and against the customer's words: a budget must appear in the customer's text since the brief began, the same idea as _size_was_said. Reset the brief when a new request starts (a new_request flag from the model plus a new person or category). search_products fills missing arguments from the brief. The prompt shows the brief, and history shrinks to the current brief's turns plus one-line summaries of earlier ones. Generalises: yes; the fields are generic and their values come from the catalogue.
  risk: Medium. A wrong reset drops a real constraint, so the eval needs 'continue' vs 'new topic' cases. It is more schema for the model to fill, and a weak model fills it worse, which ties this lever to lever 6.
- [high, 2d] 9. Brand-configurable prompt, and taking the ethnic-wear assumptions out of the code-side layer
  fixes: Needed before the T-shirt pilot; stops rules written for ethnic wear from misfiring on other catalogues. How: a prompt template with the brand name, a 'what we sell' line generated from the catalogue's categories, delivery, return and exchange policies from brand settings, and a few worked examples per vertical. Move per-brand text into brand config: the greeting (webhook.py:425), HELP (405-418), OFF_TOPIC (assistant.py:437), the checkout description (checkout.py:27) and the chat.py intro (chat.py:79). Replace _GARMENTS, _MENS_GARMENTS/_WOMENS_GARMENTS, _OCCASIONS and _FUNCTIONS with vocabularies built from the brand's categories, tags and variant options, plus an optional per-brand synonyms file. Replace the EW\d{3} matchers (selection.py:385, assistant.py:446, :581) with a per-brand SKU or handle lookup. Shorten the prompt by deleting rules that code already enforces.
  risk: Regressions on the ethnic store, so keep it in the eval as brand #0.
- [medium, 1.5d] 10. Voice notes: speech-to-text feeding the same text pipeline
  fixes: New capability, and access for customers who prefer voice (common on WhatsApp in India). How: accept message.type 'audio' (voice=true, audio/ogg with opus). Add whatsapp.download_media(media_id): GET /v21.0/{media-id} with the brand's token to get {url, mime_type}, then GET that url with the same bearer token (the URL expires within minutes). Send the bytes to Groq's audio/transcriptions endpoint with whisper-large-v3-turbo, using the prompt parameter to seed brand vocabulary (product names, 'checkout', sizes). Cap duration at about 60 s and check file size. Then call _handle_text(transcript), so commands, numbers and the assistant all work by voice. Store and log the turn as '[voice] ...' with path 'voice'. Echo 'I heard: ...' for very short or low-confidence transcripts. Hinglish: Whisper may output Devanagari, so ask for romanised output or make the code-side layer tolerate it (the LLM handles both).
  risk: Transcription errors on product names and numbers ('eleven' vs '11' needs number-word mapping). Adds 1-2 s inside the 25 s typing window. Voice is personal data, so do not keep the audio. Cost is negligible (about $0.04 per hour, with a 10 s minimum per request).
- [medium, 1d] 11. Fix owner-training feedback
  fixes: Defective few-shot examples and product boosts leaking between requests. How: store the model's own message, not the rendered reply, and let the owner rate 'good wording' separately from 'good products'. Exclude replies that a guard altered. Look up guidance and ranking with the same contextual text used when rating, or better with the extracted brief (category, occasion, who), never the model's query string. Key product boosts on brief fields, not budget text. Re-derive thresholds whenever the embedder changes, and scope all training by brand.
  risk: Low. Existing ratings keyed on bare follow-ups (feedback 14-17) should be re-keyed or retired.
- [medium, 1d] 12. Typo-tolerant matching against a vocabulary built from the catalogue
  fixes: Typos that defeat code-side routing and filters ('shervani', 'accessiroes', 'weeding', 'sizr', 'chedckout'). How: before the regex layer, correct tokens against a vocabulary built from the catalogue (categories, colours, tags, words in product names) plus the command words, using rapidfuzz or SymSpell (edit distance 1 for words of 5 letters or fewer, 2 for longer). Keep the original text for the LLM. After the Postgres move, use pg_trgm similarity for keyword search. Generalises: yes.
  risk: Wrong corrections ('tee' to 'tie'). Correct only to vocabulary words and only when the match is unambiguous. Never fuzzy-match numbers or sizes.
- [low, 0.5d] 13. Replace the string-cutting guards with rules on the reply's structure
  fixes: Fragments, the cart printed twice, and item counts that mix units and lines. How: send_reply's message is limited to at most 2 sentences with no product names or prices. On a violation, ask for one rewrite; if it still fails, use a code template ('Here are a few options for {occasion}:') instead of cutting mid-sentence. When attach is set, drop model sentences that restate the attached data. Code writes the count wording, in lines vs units.
  risk: Low. Fragments are already rare since adb0f6b.
- [medium, 4d] 14. Retrieval upgrade, done as part of the planned Postgres + pgvector move
  fixes: Weak colour and term matching, typos in search, and the scale-up to many brands. How: products and variants in Postgres with brand_id. Use an exact pgvector scan per brand: catalogues of hundreds of items do not need HNSW, which also removes the missed-item workaround at retrieval.py:391-399. Hybrid search: Postgres full-text plus pg_trgm plus vector, fused with reciprocal rank fusion, which catches exact terms like 'black', 'oversized', SKUs and typos. Replace MiniLM-L6 with a stronger small embedder (bge-small-en-v1.5 or e5-small-v2, multilingual-e5-small for Hinglish; OpenAI text-embedding-3-small costs cents per catalogue). Re-derive MAX_DISTANCE and SIMILAR afterwards. Optionally rerank the top 20 with a cross-encoder on CPU. Generalises: yes.
  risk: MAX_DISTANCE 1.55 and SIMILAR 0.75 were tuned for MiniLM and will break silently on a new embedder. RAM is tight on a Rs 1,000 VPS. On small catalogues the enforced filters and the model choice matter more than the embedder.
- [medium, 4d] 15. Image search: embeddings of product photos, plus a vision model's caption to set the filters
  fixes: New capability: a customer sends a photo or an Instagram screenshot and gets similar products. How: accept message.type 'image' (and its caption), and download it as for voice. (a) Embed it with an image-text model (open_clip ViT-B/32 or SigLIP-base via ONNX on CPU, or a hosted multimodal embedding) and find the nearest product-image vectors, per variant image and scoped to the brand, in pgvector. (b) Ask qwen/qwen3.8-27b on Groq (vision with JSON mode) for {category, colour, gender, pattern, style}, and apply the same enforced filters as lever 7. Show the top 3-4 through _list_reply and _record_shown, so '2', ADD and 'Not for me' work. When nothing is close enough (a distance threshold), say so and offer the nearest in the same category and colour. Generalises: yes. For T-shirts, colour and print dominate, which suits CLIP.
  risk: Customer photos (worn by a person, screenshots) look different from studio product shots, so measure the hit rate on 20+ labelled photos first. torch plus CLIP adds 0.5-1 GB of RAM to the VPS. Customer photos are personal data, so do not store them.
- [medium, 2d] 16. Remove the intent-guessing regexes once the brief and a stronger model are measured to carry intent
  fixes: The overlapping, English- and ethnic-specific heuristics that cause 'who wears it' errors and parroted hints. Keep the code-side command layer (numbers, ADD/REMOVE/SIZE/CART/CHECKOUT, product codes, address collection) and the fact checks (amounts, sizes, ids, the action ledger, consent checked against the customer's words). Retire _wearer, _THEIR_FUNCTION, _who_hint, _ASKS_REORDER and the _is_lookup phrase lists in favour of an intent-and-fields answer the model returns and code checks.
  risk: Medium. The harness must show that each removal causes no regression.

- Model settings, read from the code and from the non-secret lines of backend/.env: LLM_MODEL=openai/gpt-oss-20b on Groq, LLM_REASONING_EFFORT=low. LLM_FALLBACK_MODEL is unset, so the code defaults apply (gpt-oss-120b, then qwen/qwen3.8-27b). Other settings: temperature 0.3, max_tokens 1500 (gpt-oss reasoning tokens count against this), 12 s timeout, 0 SDK retries, MAX_ROUNDS 5, TURN_BUDGET_S 25 (assistant.py:36-40, :348-369).
- Memory: 12 messages stored (user text up to 500 characters, bot text up to 700; webhook.py:772, repository.py:148), 8 sent to the model, each cut to 350 characters (assistant.py:790).
- Prompt size, estimated from source (not measured): system prompt about 3.6k characters (about 900 tokens), tool schemas about 500 tokens, CUSTOMER block plus hints plus owner examples 150-450, history up to about 700. That is about 2.2-2.8k input tokens per model call. A normal turn makes 2-3 calls (search, then send_reply, plus one per guard retry), so about 5-8k input tokens per customer message, well above the 1,000-1,500 per call in CLAUDE.md.
- At Groq's free 8k tokens per minute per model, that is about one customer message per minute per model: the pilot needs the paid tier.
- The per-customer context is appended to the system message after the static prompt. Keep it that way so the static prefix stays cacheable (Groq and Moonshot both discount cached input).
- The split is sound and should be kept: code does exact commands and writes all facts (lists, prices, cart, orders, Pay Now), and those were never wrong in the logs. Failures cluster in two places: intent guessed by regex, and free text describing actions. Direction: the model decides intent and fills fields; code checks them against data and writes facts and action confirmations.
- What carries over to any catalogue: code-written lists, prices, cart and orders; tools bound to the sender's user_id; the rupee-amount check; the idea of the claim guard; add_to_cart requiring the customer to ask, with a size they typed (_size_was_said); the code-shape filter; relaxing filters with an honest note; number, name, ADD/REMOVE/SIZE/CART/CHECKOUT command routing (S-XXL sizes suit T-shirts); BUY AGAIN; 'Not for me'; address parsing (India-wide); typing indicator and send retries; owner rating as a concept.
- What does NOT carry over: the store description in SYSTEM_PROMPT (assistant.py:64-66, :80, :437); _GARMENTS, _MENS_GARMENTS/_WOMENS_GARMENTS, _OCCASIONS, _OCCASION_TAGS, and hiding accessories unless asked (retrieval.py:78-168, :421); the wedding 'who wears it' heuristics (_FUNCTIONS, _THEIR_FUNCTION, _wearer at assistant.py:697-716); the EW\d{3} product-code matchers (selection.py:385, assistant.py:446, :581); UK shoe-size rules; the 'ethnic wear' default query (retrieval.py:461); the brand name in the greeting, HELP, checkout and chat.py intro. The chat.py fallback depends on parse_query and will be weak for T-shirts until the vocabulary comes from the catalogue.
- The system assumes one shop throughout. The catalogue is a JSON file (catalog.py:20). There is one Chroma collection named 'products' (retrieval.py:30, ingest_catalog.py:77). One WhatsApp token and phone number come from env (whatsapp.py:48-50), and the media cache is keyed by file name (whatsapp.py:128). users, sessions, cart_items, bot_replies and feedback have no brand_id. For several brands: route by entry.changes.value.metadata.phone_number_id to a brand record (encrypted token, catalogue, prompt variables, policies), and add brand_id to every table and every vector query. One phone number messaging two brands must be two separate customer records.
- Shopify changes the product model. Colour and size are variant options, with a variant id and stock per colour-size pair, and a variant image. Today stock is per size only and the cart holds (product_id, size). Carts, the sizes in the context block, add_to_cart and image search must work at variant level, and checkout becomes Storefront API cartCreate plus cartLinesAdd, then checkoutUrl. Order status and exchanges come from Admin API webhooks (orders, fulfillments), not our own orders table.
- WhatsApp limits on launch features: abandoned-checkout recovery is a message the business starts outside the customer's 24-hour window. That needs approved marketing templates, the customer's opt-in, and per-message fees. whatsapp.py sends only free-form messages, which work only inside the 24-hour window (whatsapp.py:93-100). An unregistered business also starts on Meta's lowest messaging limits.
- Media plumbing needed for image and voice. In receive_message (webhook.py:1141-1153), branch on message.type: 'image' carries image.id, mime_type and an optional caption; 'audio' carries audio.id, mime_type and voice=true. Pass a media descriptor through _answer_and_send and _handle_incoming. Add whatsapp.download_media: GET /v21.0/{media-id} with the bearer token to get the url, then GET the url with the same bearer, in the background task. The existing duplicate check (_first_delivery) and typing indicator apply unchanged. Transcripts re-enter _handle_text; image results go through _list_reply and _record_shown. Keep neither photos nor audio, and store only a text trace ('[photo: black graphic tee]', '[voice] ...') in memory and logs.
- There are two LLM callers with different settings. chat.py's intro (chat.py:65-104) uses LLM_MODEL with no fallback, a separate timeout and its own client; the assistant has the fallback chain. Put one LLM module in charge of provider, base_url and key for each role (tool-calling chat model, vision model, speech-to-text, eval judge), so that trying Kimi or qwen-vision is a configuration change.
- Two thresholds are tuned to MiniLM squared-L2 and cosine scores: MAX_DISTANCE 1.55 (retrieval.py:36) and SIMILAR 0.75 (training.py:36). Any change of embedder, including the move to pgvector, must re-derive them, or retrieval and owner training degrade without any error.
- Observability: tool calls, their arguments and token counts are only printed to stdout (assistant.py:372, :907). Code-path turns (numbers, ADD, CHECKOUT, button taps) are remembered but not logged (webhook.py:901-904). The brand dashboard metrics (conversion, deflection, hand-offs) and the eval both need a per-turn trace table: path, tools, effects, model, latency, tokens, cost.
- Hosting within about Rs 1,000 a month: moving to pgvector removes the Chroma container and its RAM. MiniLM or bge-small plus Postgres fit a 2 vCPU / 4 GB VPS (about Rs 400-600). CLIP or SigLIP with torch adds 0.5-1 GB, so export to ONNX or run embedding at ingest time only. The in-memory message dedupe (webhook.py:1052) and FastAPI background tasks lose state on restart, so for several brands move dedupe to a unique constraint on message_id in the database.
- The logs cannot represent real customers: all 54 logged turns come from the developer's own account, and command paths are not logged. Avoid adding more regexes fitted to these phrasings. The pilot should first gather real (anonymised) traffic with full traces, and the eval should grow from that.

# EVAL PROPOSAL
Build scripts/eval_conversations.py with case files in evals/<brand>/*.yaml. It is a live-model, multi-turn harness, sitting between test_assistant.py (a scripted fake model that checks plumbing) and eval_retrieval.py (no LLM, checks ranking).
(1) Cases. Turn each logged failure and each good pattern into a scripted conversation, about 50 from the 54 bot_replies. Each case seeds state: cart lines with quantity and size, orders, profile, last_products_shown, and the prior messages rebuilt from bot_replies within 30 minutes. Then it plays the customer's turns and states the expected outcome. Examples: 'remove 2' with 3 in the cart leaves 1; 'i wanna pay' yields a cta_url; 'suit for wedding for me black color' after a Rs 5k request for the sister must not carry the Rs 5,000 budget; 'accessiroes for my wife' then 'wedding around 10k' returns only Footwear/Bags; '11 sizr' adds UK 11; 'chedckout' checks out. Add about 40 pilot cases on the friend's real Shopify export:
- colour ('black oversized tee under 799', then 'same in white')
- size and fit ('is M ok for 5'10 75kg', with and without a size chart)
- activity ('gym tee that doesn't show sweat')
- quantity ('remove one of the 3 black tees')
- checkout phrasings and typos
- topic switches ('now something for my sister', then 'for me, black')
- Hinglish ('bhai ke liye gym wali tee 500 tak')
- exchanges and order-status questions
Add 10 real voice notes run through Whisper, and 20 labelled customer photos or screenshots for image search, each with its expected product, category and colour.
(2) Runner. Drive routers.webhook._handle_text and _handle_incoming, the real routing rather than assistant.respond alone, against a throwaway brand and user in Postgres (the test suites already create and delete their own users). Run a matrix of configs (gpt-oss-20b low, gpt-oss-120b medium, Kimi K2.6 via Moonshot or OpenRouter, qwen3.8-27b), 3 samples per case at the production temperature. For every turn, record: the routing path (command, lookup, assistant, fallback), tool calls with their arguments and results, the final text, cards, cta_url, the cart and order diff, latency, tokens and cost.
(3) Code checks first, since most observed failures can be checked in code:
- the state diff equals the expected one (lines, quantities, sizes; no add without the customer asking; exactly the asked quantity removed)
- every add, remove, pay or order claim is backed by a recorded tool effect or a cta_url
- every size named for a product is one of its sizes, and fit advice appears only after get_size_guide
- every product shown meets the case's filters (category, gender, colour family, budget +15%, occasion or activity tag), or the reply carries a relax note
- tool arguments contain no budget or person that is absent from the current request's turns
- the bot asks for who or budget only when unknown, and never asks for something already given
- no fragments (at least 3 words, no trailing article or preposition), the cart printed once, count wording matching lines or units
- turns to cart and turns to Pay Now on purchase scripts, and latency within 25 s
(4) An LLM judge only for what code cannot check: fit to nuance (night vs daytime, guest vs groom, gym vs lounge), whether the question asked was the right one, repetition of earlier replies, tone and length. The judge should be a stronger model from a different family than the one under test. It gets the catalogue facts and tool results and scores a fixed 1-5 rubric per criterion, with a required quoted justification. Calibrate it on about 40 turns labelled by the owner, targeting at least 85% agreement, because the owner's thumbs-ups were lenient (replies with fragments were approved).
(5) Reporting and gating. Report pass counts per failure mode for each config (with small numbers, show counts, e.g. 7/9, not bare percentages), p50/p95 latency, and rupees per 100 conversations. Save each run as JSON and diff it against the baseline. Merge only with no regression in the code checks and a judge score that does not fall. Run on Groq's paid tier: at about 5-8k input tokens per customer message, the free 8k tokens per minute per model would stretch one matrix over hours. A full run costs roughly $1-5.
(6) Keep the harness fed. Log every path (commands, buttons, voice, image), with tool traces, model, latency and tokens, into bot_replies, so real pilot traffic keeps producing new cases. Today only free text reaching the assistant or a lookup is logged, and tool calls are only printed to stdout (assistant.py:907; webhook.py:901-904).
