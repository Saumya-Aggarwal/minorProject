# Research 27 Sep 2026: shopify-connector

> Raw findings from the 27 Sep research run (read-only agents). The fact-check pass did not run (session limit); four key claims were checked by hand afterwards: GPT-6 Luna price and function-calling rule (its release date is 18 May 2026, not 22 Sep), Kimi line-up and retirements, Meta charging service messages from 1 Oct 2026, Shopify's `shopifyapp` package. Everything else: re-check against the linked source before relying on it. Decisions drawn from this are in /plan.md.


- [high] (1. App type: creation) Since 1 Jan 2026 you can no longer create new custom apps in the Shopify admin. New apps are created in the Dev Dashboard (dev.shopify.com) or with Shopify CLI, then installed on the store. Legacy admin apps that already exist keep working.
  The old way of getting a token (the store owner clicks 'Develop apps' and copies it from the admin) is gone for new integrations. Every brand needs an app that is installed on its store.
  src: https://changelog.shopify.com/posts/legacy-custom-apps-can-t-be-created-after-january-1-2026
- [high] (1. Distribution: custom vs public) Custom distribution installs through a generated link on one store. The only multi-store options are stores in one Plus organization, plus transfer-disabled dev stores. It needs no Shopify review and cannot use the Billing API. Public (App Store) distribution needs app review and lets you charge through Shopify billing. The choice is permanent: 'You can't change the distribution method after you select it.'
  Steps: Dev Dashboard > app Home > Distribution card > Select distribution method > Custom > enter the store's myshopify.com domain > Generate link > send the link to the store owner, who clicks Install. A non-Plus store gets one store per custom app. For 5-20 brands on custom distribution that means one Dev Dashboard app per brand.
  src: https://shopify.dev/docs/apps/launch/distribution/select-distribution-method
- [high] (1. Distribution: public/unlisted requirements) An unlisted (limited-visibility) public app still needs a listing and the full App Store review. App Store requirement 1.2.1 says charges must go through Shopify App Pricing or the Billing API; billing outside Shopify is not allowed. OAuth must run right after install (2.3.2), and every App Store app must handle the mandatory compliance webhooks.
  Visibility doc: https://shopify.dev/docs/apps/launch/distribution/visibility . Public apps must also pass protected-customer-data review and use expiring offline tokens (see Auth). This is too much work for a one-store pilot. It becomes worth it at roughly 10+ self-serve brands.
  src: https://shopify.dev/docs/apps/launch/shopify-app-store/app-store-requirements
- [medium] (1. Distribution: per-brand pricing on a public app later) Since 21 Sep 2026, Shopify App Pricing allows unlimited private plans, each targeted at any number of chosen stores. That means a future public or unlisted app can still charge each brand a custom price through Shopify billing.
  The previous limits were 15 plans and 20 stores per plan. This makes a later move to one public app workable for custom B2B pricing.
  src: https://shopify.dev/changelog/unlimited-private-plans-and-target-stores-in-shopify-app-pricing
- [high] (1. One codebase, many apps) Shopify CLI can link one project to several apps with shopify.app.{config-name}.toml files (`shopify app config link`, `shopify app config use`). `shopify app deploy` releases a version that bundles the config (scopes, webhooks) with any extensions.
  This is how to run 5-20 custom-distribution apps (one per brand) from one repo: a shopify.app.<brand>.toml each, the same webhook URI with the shop taken from X-Shopify-Shop-Domain, and the same theme or pixel extensions. Extensions can only be versioned through the CLI, so Node is needed on the dev machine at deploy time.
  src: https://shopify.dev/docs/apps/build/cli-for-apps/manage-app-config-files
- [high] (2. Auth: the three grants) Token exchange is for embedded apps inside the admin (ID token from App Bridge). Authorization code grant is for standalone apps outside the admin: redirect the merchant to Shopify, then exchange the code. Client credentials is for 'server-side integrations acting on your own stores' with no merchant interaction.
  Our brand dashboard will live on our own domain, so we are a standalone, non-embedded app (embedded=false) and use the authorization code grant.
  src: https://shopify.dev/docs/apps/build/authentication-authorization/access-tokens
- [high] (2. Auth: client credentials limits) Client credentials works only when the app and the store belong to the same Shopify organization. It 'can't reach a store outside your organization, including a client's store'. Tokens last 24 h (expires_in 86399); you request a new one by repeating the POST to /admin/oauth/access_token with grant_type=client_credentials.
  Useful only for our own dev stores, as a fast dev loop. It cannot be used for the friend's store or any client.
  src: https://shopify.dev/docs/apps/build/authentication-authorization/client-credentials-grant
- [high] (2. Auth: authorization code grant mechanics) Redirect to https://{shop}/admin/oauth/authorize with client_id, scope, redirect_uri (must exactly match one set in the Dev Dashboard) and a state nonce. On the callback, verify the HMAC: drop hmac, sort the params, HMAC-SHA256 with the client secret, compare in constant time. Also check shop against ^[a-zA-Z0-9][a-zA-Z0-9\-]*\.myshopify\.com$. Then POST the code to /admin/oauth/access_token, optionally with expiring=1.
  Offline tokens (the default) are not tied to a staff member, which is what a background bot needs. Online tokens need grant_options[]=per-user and are not needed here.
  src: https://shopify.dev/docs/apps/build/authentication-authorization/access-tokens/authorization-code-grant
- [high] (2. Auth: 2026 token expiry changes) Expiring offline tokens last 1 h, with a refresh token valid 90 days. New public apps have needed them since 1 Apr 2026, and all public apps must use them by 1 Jan 2027. Custom and merchant-created apps are exempt. Request one with expiring=1. Getting a new expiring token retires older ones.
  From 28 Aug 2026 a refresh keeps the previous refresh token valid until the new one is used (https://shopify.dev/changelog/more-resilient-refreshes-for-expiring-offline-access-tokens). Recommendation: use expiring=1 from day one even on custom apps, so the token code does not have to change when a public app comes later. Keep one row per (store, app) and refresh under a DB lock.
  src: https://shopify.dev/docs/apps/build/authentication-authorization/access-tokens/offline-access-tokens.md
- [high] (2. Auth: official Python package) On 26 Aug 2026 Shopify released official framework-agnostic Python and PHP packages (`pip install shopifyapp`, v1.0), which name FastAPI explicitly. They cover request and webhook verification, token exchange (including client credentials and refresh) and an Admin GraphQL client with retries. The old shopify_python_api is deprecated.
  Repo: https://github.com/Shopify/shopify-app-python . There is no template; you compose the primitives yourself, which suits the existing FastAPI backend. There is no need for the Node/Remix template except the CLI for deploying extensions.
  src: https://shopify.dev/changelog/build-shopify-apps-in-php-and-python-with-new-official-packages
- [high] (3. Protected customer data: levels and custom apps) Level 1 is customer data other than name, address, phone and email. Level 2 covers name, address (both billing and shipping), email and phone. Access table: public app 'Requires review' for both levels. Custom app 'Always available' for both levels. Admin-created custom app: Level 1 always, Level 2 'varies by plan'. Unapproved fields come back null, and a GraphQL request for an unapproved type returns 200 with an errors entry.
  So a custom-distribution app for the pilot can read phone, name and address on orders, checkouts and customers without a review. It still has to meet the data-protection duties: minimisation, a retention policy, encryption in transit and at rest, and access logging for Level 2.
  src: https://shopify.dev/docs/apps/launch/protected-customer-data
- [medium] (3. Protected customer data: practical declaration step) Shopify's webhook getting-started guide says that scopes touching private customer data (e.g. read_orders) 'require manual steps': go to API access requests > Protected customer data access, fill out only the first step, save, and reinstall. Without it, CLI registration of orders or checkouts webhooks fails with 'not approved to subscribe to webhook topics containing protected customer data'.
  This is written for Partner Dashboard apps, and the docs do not say exactly how the Dev Dashboard handles it for custom distribution. Plan to tick the fields you use (phone, name, address, email) in the dashboard even though no review is needed. Check on a dev store first (CLI issue: https://github.com/Shopify/cli/issues/3443).
  src: https://shopify.dev/docs/apps/build/webhooks/subscribe/get-started
- [high] (3. Protected customer data: pixels) Since 10 Dec 2025, web pixel extensions get PII (name, email, phone, address) only with the approved protected scopes read_customer_name / read_customer_email / read_customer_phone / read_customer_address / read_customer_personal_data. Otherwise those fields are null.
  Browse-event pixels for the pilot do not need PII. Link events to WhatsApp users through our own cart attribute or ref instead.
  src: https://shopify.dev/changelog/protected-customer-data-scopes-required
- [high] (4. Admin API scopes and the 60-day order window) read_products covers Product, ProductVariant and Collection. read_inventory covers InventoryItem and InventoryLevel. read_orders/write_orders only reach orders from the last 60 days; older ones need read_all_orders, which requires Shopify approval. read_returns/write_returns cover Return and the reverse-logistics objects. The unauthenticated_* scopes are for the Storefront API.
  60 days is enough for 'where is my order' and exchanges. Past-purchase personalisation ('buy it again') should come from our own order mirror built from webhooks rather than from read_all_orders.
  src: https://shopify.dev/docs/api/usage/access-scopes
- [high] (4. Catalogue sync with bulk operations) bulkOperationRunQuery runs a query in the background and writes JSONL, where child nodes carry __parentId. From API 2026-01 an app can run up to five bulk queries per shop at once (earlier: one). Completion arrives through the bulk_operations/finish webhook or by polling bulkOperation(id:). The result URL expires after one week. Limits: at most 5 connections, nested at most 2 levels, and pagination arguments are ignored.
  First sync: products { variants { inventoryQuantity, selectedOptions, price, compareAtPrice }, media/images } go into Postgres products/variants keyed by store_id, then embeddings go into pgvector. Keep every image URL so the planned image search can embed them. After that, stay in sync with products/* and inventory_levels/update webhooks, plus a nightly reconcile.
  src: https://shopify.dev/docs/api/usage/bulk-operations/queries
- [high] (4. Finding orders by customer phone) The orders query cannot filter by phone. Its filters include email, customer_id, name, cart_token, checkout_token, financial_status, fulfillment_status, return_status, tag, source_name, created_at and updated_at. To go from a phone number to orders: customerByIdentifier(identifier:{phoneNumber:"+91..."}) or customers(query:"phone:+91...") (read_customers), then orders(query:"customer_id:<id>").
  customerByIdentifier: https://shopify.dev/docs/api/admin-graphql/latest/queries/customerByIdentifier . More reliable: keep our own index from orders/create and orders/updated webhook payloads (order phone, customer phone, shipping and billing phone, normalised to E.164). Guest checkouts in India often have a phone that differs from the WhatsApp number. The cart_token and checkout_token filters are useful for linking an order back to a WhatsApp cart.
  src: https://shopify.dev/docs/api/admin-graphql/latest/queries/orders
- [high] (4. Fulfilment and tracking) The Fulfillment object has trackingInfo (company, number, url), status, displayStatus, estimatedDeliveryAt, inTransitAt, deliveredAt and events. It can be read with read_orders, among other scopes.
  Indian shipping apps (e.g. aggregators) write tracking into Shopify fulfillments, and fulfillments/create|update plus fulfillment_events/create webhooks push the changes. That covers the order-status feature.
  src: https://shopify.dev/docs/api/admin-graphql/latest/objects/Fulfillment
- [high] (4. Returns and exchanges) returnRequest creates a REQUESTED return that the merchant approves (returnApproveRequest) or declines (returnDeclineRequest). Its input (orderId, returnLineItems, returnShippingFee) has no exchangeLineItems. returnCreate opens a return directly and accepts exchangeLineItems {variantId, quantity}. From API 2025-07 an explicit returnProcess call confirms the exchange and creates fulfilment orders. A balance due is collected with orderInvoiceSend, and exchanges with money owed are held. Scopes: read_returns and write_returns.
  returnRequest: https://shopify.dev/docs/api/admin-graphql/latest/mutations/returnRequest ; returnCreate: https://shopify.dev/docs/api/admin-graphql/latest/mutations/returncreate . Returns work only on fulfilled line items. Webhooks: returns/request|approve|decline|update. A Built for Shopify rule that buyer self-serve returns apps must use the Customer Account API (from 1 Dec 2026) applies only to apps seeking the BFS badge (https://shopify.dev/changelog/built-for-shopify-requirements-for-returns-and-exchanges-and-subscription-apps).
  src: https://shopify.dev/docs/apps/build/orders-fulfillment/returns-apps/manage-exchanges
- [high] (5. Webhook topics and required scopes) CHECKOUTS_CREATE/UPDATE/DELETE, ORDERS_CREATE, ORDERS_UPDATED and ORDERS_FULFILLED need read_orders. FULFILLMENTS_CREATE/UPDATE and FULFILLMENT_EVENTS_CREATE need read_fulfillments. PRODUCTS_CREATE/UPDATE/DELETE need read_products. INVENTORY_LEVELS_UPDATE needs read_inventory. RETURNS_* need read_returns. CUSTOMERS_MARKETING_CONSENT_UPDATE needs read_customers. APP_UNINSTALLED, APP_SCOPES_UPDATE and BULK_OPERATIONS_FINISH need no scope. CARTS_CREATE/UPDATE (online store carts) need read_orders.
  Where a topic lists marketplace or buyer-membership scopes too, those are alternatives. For a D2C brand the plain scopes are enough.
  src: https://shopify.dev/docs/api/admin-graphql/latest/enums/WebhookSubscriptionTopic
- [high] (5. Subscribing: app-specific vs shop-specific) Shopify recommends app-specific subscriptions in shopify.app.toml: one config for every shop, and failing subscriptions are not deleted. Shop-specific subscriptions made through GraphQL webhookSubscriptionCreate are deleted when they keep failing. Both support filter expressions and include_fields, and delivery can be HTTPS, Google Pub/Sub or EventBridge.
  Also: 'Events' (field-level triggers) are in developer preview on the unstable API, and the docs say to 'keep using webhooks for production' (https://shopify.dev/docs/apps/build/events-webhooks).
  src: https://shopify.dev/docs/apps/build/webhooks/subscribe
- [high] (5. HMAC verification and delivery rules) Verify X-Shopify-Hmac-SHA256 = base64(HMAC-SHA256(raw body, client secret)), compared in constant time on the raw bytes before any JSON parsing. Shopify allows 1 s to connect and 5 s for the whole request, retries 8 times over 4 hours, and deletes shop-specific subscriptions after 8 consecutive failures. De-duplicate on X-Shopify-Webhook-Id; X-Shopify-Event-Id links related deliveries.
  The existing pattern fits: return 200 at once and process in a background task, as the WhatsApp and Razorpay webhooks already do. Key each shop's secret by app, since each brand's custom app has its own client secret.
  src: https://shopify.dev/docs/apps/build/webhooks/subscribe/https
- [high] (5. Mandatory compliance webhooks) Every App Store app must handle customers/data_request, customers/redact and shop/redact (set with compliance_topics in shopify.app.toml). Answer with a 2xx, finish the action within 30 days, and return 401 when the HMAC is invalid. shop/redact arrives 48 h after uninstall.
  The docs tie this to App Store distribution. Implement them on the custom apps anyway: it is cheap, it covers India's DPDP obligations, and a later public app will need them. Pair with app/uninstalled: stop sync, revoke the Storefront token, keep data until shop/redact.
  src: https://shopify.dev/docs/apps/build/compliance/privacy-law-compliance
- [high] (5. Abandoned checkouts: Admin API) The abandonedCheckouts query needs read_orders plus the manage_abandoned_checkouts permission. A checkout counts as abandoned 'when a customer adds contact information but doesn't complete their purchase'. AbandonedCheckout fields: abandonedCheckoutUrl, customAttributes, note, discountCodes, customer, billingAddress, shippingAddress, lineItems, totals, completedAt, createdAt and updatedAt. It has no top-level phone, email or marketing-consent fields.
  Query filters: created_at, updated_at, status (open/closed), recovery_state and email_state (https://shopify.dev/docs/api/admin-graphql/latest/queries/abandonedCheckouts). customAttributes is the useful part: attributes we set on the cart show up here, so an abandoned checkout maps back to a WhatsApp conversation even without a phone number.
  src: https://shopify.dev/docs/api/admin-graphql/latest/objects/AbandonedCheckout
- [medium] (5. Abandoned checkouts: webhook payload has phone and SMS consent) The REST checkout representation, which checkouts/* webhook payloads use, includes phone, email, sms_marketing_phone, buyer_accepts_marketing, buyer_accepts_sms_marketing ('Whether the customer would like to receive SMS updates from the shop'), abandoned_checkout_url, token, cart_token, note_attributes, landing_site and completed_at.
  The REST Admin API itself is legacy, but webhook payloads are still REST-shaped. SMS consent is not the same as WhatsApp consent (see the Meta finding). Recovery flow: on checkouts/update with a phone and completed_at null, schedule a reminder. Cancel it on orders/create with the same checkout_token or cart_token. Check whether the merchant's own Shopify abandoned-checkout emails are on, so the customer isn't reminded twice.
  src: https://shopify.dev/docs/api/admin-rest/latest/resources/abandoned-checkouts
- [medium] (5. WhatsApp side of recovery (Meta policy)) Meta's opt-in may be general rather than WhatsApp-specific, but it must clearly name the business. Abandoned-cart nudges are Marketing-category templates; order confirmations and shipping updates are Utility.
  Template categories: https://developers.facebook.com/docs/whatsapp/updates-to-pricing/new-template-guidelines/ . For the pilot: if the checkout started from a WhatsApp chat within the last 24 h, send free-form text in the service window. Otherwise send only when we hold a recorded opt-in (from the cart-page checkbox or in chat), using a Marketing template.
  src: https://developers.facebook.com/docs/whatsapp/overview/getting-opt-in/
- [high] (6. Storefront API auth options) Tokenless access covers products, collections, search, pages and cart read/write, capped at query complexity 1,000, with no tags, metafields, metaobjects or customer data. A public token (X-Shopify-Storefront-Access-Token) is created with Admin storefrontAccessTokenCreate, up to 100 per shop, and carries unauthenticated_read_product_listings, unauthenticated_write_checkouts, unauthenticated_read_checkouts and unauthenticated_read_selling_plans. A private token (Shopify-Storefront-Private-Token) comes from the Headless channel or a delegate token and is server-only.
  Endpoint: https://{shop}.myshopify.com/api/2026-07/graphql.json. storefrontAccessTokenCreate: https://shopify.dev/docs/api/admin-graphql/latest/mutations/storefrontAccessTokenCreate . With the unauthenticated_* scopes on our app we can mint the brand's token ourselves after install, so the owner does not have to install Headless.
  src: https://shopify.dev/docs/api/storefront/latest
- [high] (6. Server-side calls: buyer IP and throttling) Buyer traffic has no fixed per-minute limit, but automated traffic and checkout creation are limited ('200 Throttled'). Server-side calls should send Shopify-Storefront-Buyer-IP. Without it Shopify 'can't differentiate requests from different buyers, which can result in throttled API requests, limited bot protection, and unauthenticated flows at checkout.' Request checkoutUrl when the buyer is ready to go, and request it again if it is stale.
  This is a real risk for a WhatsApp bot, because we never learn the buyer's IP. Keep volume low: create the cart only at CHECKOUT, not on every ADD. Fall back to a cart permalink. Test on a dev store whether checkout behaves differently.
  src: https://shopify.dev/docs/storefronts/headless/building-with-the-storefront-api/cart/manage
- [high] (6. Cart mutation, buyer prefill, attributes) cartCreate accepts lines (merchandiseId, quantity), buyerIdentity (email, phone, countryCode, customerAccessToken, companyLocationId, preferences), attributes (up to 250 key-value pairs), note and discountCodes. buyerIdentity.preferences 'are used to prefill fields at checkout'. The returned cart has a checkoutUrl that 'redirects customers through Shopify's web checkout'. The cart ID has the form <token>?key=<secret>.
  Set countryCode=IN and phone = the WhatsApp number in E.164. Also set attributes {munim_conv: <opaque id>, munim_store: <id>, source: whatsapp}. Send checkoutUrl as the WhatsApp CTA button, replacing the Razorpay Pay Now for Shopify brands.
  src: https://shopify.dev/docs/api/storefront/latest/input-objects/CartBuyerIdentityInput
- [medium] (6. Attribution of resulting orders) Cart attributes are meant to carry into the order's customAttributes (note_attributes), but a Sept 2025 community thread reports this fails inconsistently. Channel-level attribution only happens when the checkout is created with a storefront token belonging to a sales-channel app.
  Use several signals to attribute an order to Munim: (1) our cart_token/checkout_token recorded at checkout time, matched through the orders query filters cart_token: and checkout_token: or the orders/create payload; (2) note_attributes when they arrive; (3) customer phone. Report 'orders influenced by WhatsApp' on the brand dashboard from this match, not from Shopify's channel reports. A 30 Jun 2026 changelog added order-attribution configuration only for sales-channel apps.
  src: https://community.shopify.dev/t/cart-attributes-rarely-carry-over-to-customattributes-on-order-object/23367
- [medium] (6. Plan requirements for checkoutUrl) The docs put no Shopify Plus requirement on Storefront cart plus checkoutUrl. It hands off to the store's standard web checkout, and the Checkout API it replaced was shut down on 1 Apr 2025. The Headless channel app is not offered on the Starter plan (Basic or higher is needed).
  If the friend's store is on Starter, check whether tokenless or app-minted Storefront carts still work there. The cart permalink is the fallback that works on any plan with an online store.
  src: https://community.shopify.com/t/make-the-headless-app-available-on-the-starter-plan-5-is-it-possible/630935
- [high] (6. Zero-API fallback: cart permalinks) https://{shop}/cart/{variant_id}:{qty},{variant_id}:{qty} supports checkout[email], checkout[shipping_address][first_name|last_name|address1|address2|city|province|country|zip], note, attributes[...], ref (shown in the order's Conversion summary), discount, access_token (channel attribution), storefront=true and payment=shop_pay. There is no checkout phone parameter. Permalinks cannot get past a storefront password, and selling plans don't work.
  This works on any Shopify store with no app installed, which makes it ideal for a demo before the owner installs anything. Only numeric variant IDs are needed, and /products.json provides them.
  src: https://shopify.dev/docs/apps/build/checkout/create-cart-permalinks
- [high] (7. Theme app extensions (no Plus needed)) App embed blocks inject before </head> or </body> (targets head, compliance_head, body) and work on both vintage and Online Store 2.0 themes. They are 'deactivated after an app is installed' and the merchant must switch them on in the theme editor. A deep link opens that switch directly: https://<shop>/admin/themes/current/editor?context=apps&template=...&activateAppId={api_key}/{handle}. App blocks (inline) need JSON-template sections that accept @app.
  Use one app embed for the floating 'Chat on WhatsApp' button (a wa.me link pre-filled with the product handle or code). The same script can add an opt-in checkbox near the cart form and write it with POST /cart/update.js {attributes:{whatsapp_optin:'yes', munim_ref:...}} (https://shopify.dev/docs/api/ajax/reference/cart). Positioning depends on the theme's DOM, so test it on the friend's theme.
  src: https://shopify.dev/docs/apps/build/online-store/theme-app-extensions/configuration
- [high] (7. Web Pixels extension) Web pixels need the write_pixels and read_customer_events scopes. The app must activate the pixel itself after install with the webPixelCreate mutation (settings JSON). It runs in a strict sandbox and is gated by customer privacy settings. It subscribes to standard events: page_viewed, product_viewed, collection_viewed, search_submitted, product_added_to_cart, product_removed_from_cart, cart_viewed, checkout_started, checkout_contact_info_submitted, checkout_address_info_submitted, checkout_shipping_info_submitted, payment_info_submitted, checkout_completed.
  Event list: https://shopify.dev/docs/api/web-pixels-api/standard-events . Callbacks fire only after consent where consent is required. Leave pixels out of the pilot and use webhooks plus cart attributes for metrics. Add them later for browse-to-WhatsApp analytics.
  src: https://shopify.dev/docs/apps/build/marketing-analytics/build-web-pixels
- [high] (7. Checkout UI extensions) Checkout UI extensions on the information, shipping and payment steps are available only on Shopify Plus. Extensions on the Thank you and Order status pages are available on all plans except Starter.
  Thank-you page note: https://shopify.dev/docs/apps/build/checkout/thank-you-order-status . A WhatsApp opt-in inside checkout is therefore not possible for a non-Plus brand. Put it on the cart page (app embed) or ask in chat. A 'Get order updates on WhatsApp' block on the Thank you page is possible on Basic and above.
  src: https://shopify.dev/docs/api/checkout-ui-extensions
- [medium] (8. Catalogue without the owner) Most Shopify stores serve /products.json publicly: 30 products by default, limit up to 250, page=N in practice. It is unofficial and not a replacement for the Admin API; some stores block or rate-limit it. The official owner-free options are tokenless Storefront API (products, collections, search, cart; complexity cap 1,000) and Shopify's UCP endpoints at https://{shop}/api/ucp/mcp. Those endpoints (Storefront Catalog: search_catalog, lookup_catalog, get_product; Cart MCP: create_cart, get_cart, update_cart, cancel_cart, which return a continue_url) accept Anonymous-tier requests that carry an agent-profile URL.
  Catalog MCP: https://shopify.dev/docs/agents/catalog/storefront-catalog ; Cart MCP: https://shopify.dev/docs/agents/carts-and-checkout/cart-mcp . Merchants can control or opt out of agentic channels in Sales channels > Agentic (help.shopify.com/en/manual/online-sales-channels/agentic-storefronts). For demos, pull the friend's live catalogue through tokenless Storefront or /products.json today, before any install. Stock quantities, orders and returns still need the installed app.
  src: https://shopify.dev/docs/agents/profiles/auth-and-rate-limiting
- [high] (8. Development stores and CSV import) Free dev stores are created in the Dev Dashboard (Stores > Create store > Dev) or with `shopify store create dev --name --plan --demo-data --country`. Plans can be Basic, Grow, Advanced or Plus, so Plus-only features can be tested. Limits: 250 per organization, no real transactions (Bogus gateway or test mode), not transferable to a client. Products can be imported through Products > Import from a CSV of at most 15 MB, with one row per variant.
  CSV import help: https://help.shopify.com/en/manual/products/import-export/import-products . Dev stores in our org can use client credentials, and a custom-distribution app can also be installed on transfer-disabled dev stores. Ask the friend for a product CSV export (Products > Export) and import it into a dev store to build the whole flow before touching the live store. Sorting that CSV in a spreadsheet can break image links.
  src: https://shopify.dev/docs/apps/build/dev-dashboard/development-stores
- [high] (9. Steps that need the store owner) Only the owner, or staff or a collaborator with 'Manage and install apps and channels' (plus 'Approve app charges' for billing), can install an app or approve new required scopes. New required scopes prompt re-approval the next time the app is opened. Collaborator access means the partner enters the owner's 4-digit request code in the Dev Dashboard and the owner approves it; collaborators don't count toward staff limits and can't be Administrator. Activating an app embed in the theme editor is also a merchant action.
  Scope re-approval: https://shopify.dev/docs/apps/build/authentication-authorization/manage-access-scopes . The owner's checklist: (1) click our install link and approve scopes, (2) optionally approve a collaborator request so we can debug in their admin, (3) click the activateAppId deep link and Save, (4) set up returns/exchange rules in Shopify settings, (5) confirm the WhatsApp number or WABA and the business name used in opt-in text.
  src: https://help.shopify.com/en/manual/your-account/users/security/collaborator-accounts
- [high] (10. WooCommerce equivalent) REST API v3 (/wp-json/wc/v3/products, /orders, /customers) uses a consumer key and secret over HTTPS Basic Auth. /wc-auth/v1/authorize (app_name, scope=read_write, user_id, return_url, callback_url) lets the owner approve in one click, and the keys are POSTed to our callback_url. Webhooks (order.created, product.updated, ...) are signed with X-WC-Webhook-Signature = base64 HMAC-SHA256 of the body with the webhook secret.
  Checkout hand-off: WooCommerce 10+ shareable URLs /checkout-link/?products=ID:QTY,ID:QTY&coupon=CODE (variations by variation ID) (https://developer.woocommerce.com/docs/best-practices/urls-and-routing/checkout-urls/). The unauthenticated Store API /wp-json/wc/store/v1/cart is for headless carts. Core has no abandoned-checkout, returns or tracking APIs; those need plugins or our JS snippet.
  src: https://woocommerce.github.io/woocommerce-rest-api-docs/
- [medium] (10. Custom / Next.js sites) Keep ingestion platform-neutral by accepting a product feed in the Google Merchant Center product data format: id, title, description, link, image_link, price, availability, item_group_id for variants, plus size, colour and gender. Most custom sites can produce it, or they can push to our REST ingest API.
  Pair it with (a) our HMAC-signed order-status webhook that the site calls, (b) a small JS snippet giving the WhatsApp button, opt-in and events (the non-Shopify version of the app embed), and (c) checkout either as a deep link into their cart (if they have one) or through our existing Razorpay flow.
  src: https://support.google.com/merchants/answer/7052112?hl=en

# RECOMMENDATION
PILOT BUILD (friend's Shopify store, ~2-3 weeks solo, Rs 0 Shopify cost)

Step 0: owner-free demo, days 1-2.
- Read the friend's live catalogue through tokenless Storefront API (https://{shop}.myshopify.com/api/2026-07/graphql.json), with /products.json as a fallback, into Postgres with store_id, then into pgvector.
- Hand off checkout with a cart permalink: /cart/{variant}:{qty}?attributes[munim_conv]=..&ref=munim.
- This shows the full chat -> Shopify checkout loop before anything is installed.
- Also import the friend's product CSV into a free Dev Dashboard dev store (Basic plan). Develop against it with a client-credentials token (24 h tokens; only works for stores in our own org).

Step 1: the connector app.
- Create one Dev Dashboard app per brand, custom distribution, non-embedded (embedded=false). Run it from one repo with shopify.app.<brand>.toml files.
- Authorization code grant with expiring=1 and refresh, using Shopify's official `shopifyapp` Python package (FastAPI-compatible, released 26 Aug 2026).
- Generate the install link for the friend's myshopify domain.
- In the Dev Dashboard, tick the protected customer data you use: phone, name, address, email. Custom apps get Level 1 and 2 without review.

Minimal scopes:
- read_products, read_inventory, read_orders, read_fulfillments, read_customers, read_returns, write_returns.
- unauthenticated_read_product_listings, unauthenticated_write_checkouts, unauthenticated_read_checkouts. With these, after install, call storefrontAccessTokenCreate to mint the brand's Storefront token. The owner never touches the Headless channel.
- Leave pixel scopes and read_all_orders out of the pilot.

Webhooks (app-specific, in the toml, api_version 2026-07; all go to one FastAPI route):
- app/uninstalled, products/create|update|delete, inventory_levels/update, orders/create, orders/updated, fulfillments/create|update, checkouts/create|update, returns/request|approve|decline, bulk_operations/finish.
- Compliance topics: customers/data_request, customers/redact, shop/redact.
- On each delivery: verify X-Shopify-Hmac-SHA256 on the raw body with that brand's secret, return 200 within 5 s, de-duplicate on X-Shopify-Webhook-Id, and process in a background task.

Features in the pilot:
1. Catalogue sync. Run bulkOperationRunQuery for products, variants, stock and all image URLs into JSONL, then into Postgres and pgvector. Keep it current with webhooks, plus a nightly reconcile. Storing the image URLs now is what the planned image search will need.
2. Checkout. At CHECKOUT, call Storefront cartCreate with:
   - the lines
   - buyerIdentity {phone: WhatsApp E.164, countryCode: IN}
   - attributes {munim_conv, munim_store}
   Send checkoutUrl as the WhatsApp CTA button, and record cart_token. Fall back to the permalink if Storefront throttles (we cannot send Shopify-Storefront-Buyer-IP). Attribute orders by matching the orders/create cart_token or checkout_token, then note_attributes, then phone. Send a WhatsApp confirmation (Utility template when outside the 24 h window).
3. Order status. Keep our own phone -> orders index from order webhooks. Fall back to customerByIdentifier(phoneNumber) then orders(query:"customer_id:..."). Tracking comes from Fulfillment.trackingInfo and deliveredAt. read_orders only reaches the last 60 days, which is enough here.
4. Exchanges. Collect the order line, reason and wanted size in chat, then call returnRequest (status REQUESTED). The owner approves in Shopify admin (the human hand-off). The bot tells the customer on returns/approve or returns/decline. Do not automate returnCreate(exchangeLineItems) + returnProcess + orderInvoiceSend yet.
5. Abandoned checkout. On checkouts/update with a phone and no completed_at, wait about 1 h. If the orders/create checkout_token still hasn't arrived:
   - If the checkout came from a WhatsApp chat within 24 h, send free-form text in the service window.
   - Otherwise send a Marketing template, and only if we hold a recorded WhatsApp opt-in.
   Check first whether Shopify's own abandoned-checkout emails are on.
6. Storefront UI. One theme app extension with an app embed: a floating 'Chat on WhatsApp' button (wa.me pre-filled with the product code) and an optional opt-in checkbox near the cart form, written to cart attributes through /cart/update.js. The owner switches it on with the activateAppId deep link.
7. Dashboard and metrics come from our own tables: chats, carts created, checkouts started and completed, recovered checkouts, and 'hand-off needed' flags.

Not in the pilot: Checkout UI extensions (Plus-only on the info, shipping and payment steps), web pixels, read_all_orders, public listing.

Scaling to 5-20 brands:
- Keep one custom-distribution app per brand. Install links are per store, need no review and cost nothing, and it is the same codebase and extension with N toml configs.
- When brands need a self-serve install, or there are ~10+ of them, create a NEW public app, unlisted at first. Distribution cannot be changed, so it has to be a new app. It then needs App Store review, Shopify App Pricing (private plans can now target specific stores), expiring tokens (mandatory for public apps by 1 Jan 2027), protected-customer-data review and compliance webhooks. Build all of these in from day one, so switching is only a config change.

Keeping the core platform-agnostic:
- Put a CommerceConnector interface between the bot/RAG core and each platform, with these calls: sync_catalog, apply_event, stock, build_checkout(cart, buyer) -> url, find_orders(phone), order_status, request_exchange, and parse_webhook -> normalized events (product.updated, inventory.updated, order.created, order.updated, fulfillment.updated, checkout.abandoned, return.updated).
- ShopifyConnector implements it with the APIs above.
- WooConnector: keys through /wc-auth/v1/authorize, REST v3, X-WC-Webhook-Signature webhooks, and /checkout-link/?products=ID:QTY (WooCommerce 10+).
- FeedConnector for Next.js or custom sites: a Google Merchant Center-format feed or our REST ingest API, our signed order webhook, the JS snippet, and Razorpay checkout from the existing code.

# OPEN QUESTIONS
- Which Shopify plan is the friend's store on? Starter has no Headless channel, no full theme editor, and no Thank-you-page extensions, so if it is Starter, test tokenless or app-minted Storefront carts and theme app embeds there before committing.
- Do Dev Dashboard custom-distribution apps still need the 'Protected customer data access' form filled (step 1 only) before orders/* and checkouts/* webhooks will register? The docs say custom apps have Level 1 and 2 'always available', but the webhook guide describes a manual dashboard step. Check on a dev store.
- Server-side Storefront calls cannot send Shopify-Storefront-Buyer-IP for a WhatsApp user. Does this cause throttling, or 'unauthenticated flows at checkout', at pilot volume? Needs testing. The cart permalink is the fallback.
- Do cart attributes reach the order's customAttributes/note_attributes reliably? A community report says no, so attribute primarily by cart_token/checkout_token and confirm on a dev store.
- Can a custom-distribution app get read_all_orders (orders older than 60 days) without Shopify approval? Not needed for the pilot.
- The UCP Storefront Catalog and Cart MCP endpoints allow anonymous access, but their commercial-use terms and rate limits are not given as numbers. Merchants can also opt out in Sales channels > Agentic, so they are not a guaranteed way to read a catalogue without the owner.
- Meta opt-in: is Shopify's SMS marketing consent (buyer_accepts_sms_marketing) enough to send WhatsApp Marketing templates for abandoned-cart recovery, given Meta's general-opt-in rule and India's DPDP Act? The safer course is our own WhatsApp opt-in record.
- The user's relayed request also mentions switching the bot's LLM to Kimi for image search and voice-to-text. This Shopify research does not cover that. The only link is that the connector should sync every product and variant image URL so image embeddings can be built.
